# Research: web-delivery approaches for a live PyBoy frame feed

Resolves the research question in [issue #40](https://github.com/zbloss/jev-plays-pokemon/issues/40), a child of the wayfinder map issue [#36](https://github.com/zbloss/jev-plays-pokemon/issues/36) ("Watch It Live: visual viewer for streaming").

Question: compare three ways to get PyBoy's live screen buffer into a browser page (polling a still-image endpoint, MJPEG multipart streaming, WebSocket binary frame push) against this project's actual constraints — the existing stdlib-only, read-only, loopback-bound `http.server` pattern already shipped for the decision/confidence/milestone JSON feed, a local-only OBS-browser-source-and-plain-tab audience, and a ~3.3 turns/s tactical decision cadence, not 30-60fps video — and recommend one for the follow-up decision ticket, [#41](https://github.com/zbloss/jev-plays-pokemon/issues/41), to act on. This is a research/tradeoff document; it does not implement anything.

## 1. The existing pattern this has to fit

`src/jev_plays_pokemon/stream_surface.py` is the baseline every new endpoint is judged against. Read in full for this research, it establishes:

- A `ThreadingHTTPServer` subclass (`_StreamServer`) with `daemon_threads = True`, started on its own background daemon thread via `threading.Thread(..., daemon=True).start()` — [`stream_surface.py:132-137, 168-182`](../../src/jev_plays_pokemon/stream_surface.py).
- A request handler (`_ReadOnlyRequestHandler`, subclassing `http.server.BaseHTTPRequestHandler`) that implements `do_GET` only. Its own docstring states the read-only property is structural: "`http.server` answers every other method with 501 Not Implemented on its own" — no `do_POST`/`do_PUT`/etc. exist at all — [`stream_surface.py:140-146`](../../src/jev_plays_pokemon/stream_surface.py).
- Binds to `127.0.0.1` by default, ephemeral port (`port=0`) unless fixed — [`stream_surface.py:168-171`](../../src/jev_plays_pokemon/stream_surface.py).
- Serves exactly one path (`/`), 404s everything else, and sends `Cache-Control: no-store` so pollers never see stale cached state — [`stream_surface.py:150-162`](../../src/jev_plays_pokemon/stream_surface.py).
- Zero added HTTP-layer dependency; `pydantic` is used only for the wire-shape model, not transport — [`stream_surface.py:9-13`](../../src/jev_plays_pokemon/stream_surface.py).

Cadence context: the tactical decision loop this feed would accompany runs at a budgeted **~3.3 turns/s** (~300ms/turn, p95 ~266ms measured live), and that ceiling is set almost entirely by the TypeSafe API round trip, not local work — this repo's [`docs/turn-rate-budget.md`](../turn-rate-budget.md). A frame feed only needs to keep pace with that decision cadence, not with 30-60fps game footage.

## 2. Approach A — polling a still-image endpoint

**Mechanism:** client-side JS timer (`setInterval` swapping an `<img src>` with a cache-busting query param, or `fetch` + `URL.createObjectURL`) re-requests a fresh still image (e.g. PNG) on each tick; server-side, a `do_GET` handler encodes and returns the current frame, then the connection closes — exactly the request-and-done shape `stream_surface.py`'s JSON endpoint already uses.

- **Implementation cost against stdlib `http.server`.** Zero added dependency, and it is the *same* code shape as the existing JSON handler: a `do_GET` that writes one `Content-Type`/`Content-Length` response body and returns. No new server class, no new threading model, no long-lived connection. This is the cheapest of the three to build and the most structurally identical to what's already shipped.
- **Browser/OBS compatibility.** Universally compatible — plain GET + `<img>`/`fetch` is the oldest, most compatible browser primitive there is; nothing to verify beyond "does the browser support `<img>` and JS timers," which every target (a local browser tab and OBS's Chromium-based browser source) trivially does.
- **Fit vs. the read-only/GET-only/loopback design.** Perfect fit — pure GET, request-and-done, no new HTTP verb, no persistent connection. It is the same shape as the existing surface, just with a different content type.
- **Concurrency/threading.** Identical to the existing JSON endpoint's model: each poll is a new short-lived request, handled and released by `ThreadingHTTPServer`'s one-thread-per-request model exactly as today — no new concern.
- **Downside (not itself a factor in the four required dimensions, but relevant to the final recommendation):** polling cadence is capped by the JS timer interval and each tick pays a full new-connection/request overhead; getting smooth visual updates at even ~3fps means either a fairly tight timer or accepting visible step changes. This is a real cost, just not one of implementation, compatibility, or fit.

## 3. Approach B — MJPEG multipart streaming

**Mechanism:** one persistent HTTP connection, `Content-Type: multipart/x-mixed-replace; boundary=...`, with the server writing repeated `--boundary\r\nContent-Type: image/jpeg\r\n\r\n<jpeg bytes>\r\n` parts to the same response over time; the client points a plain `<img src="...">` at the streaming endpoint and the browser itself swaps the displayed image as each part arrives.

- **Implementation cost against stdlib `http.server`.** Genuinely stdlib-buildable, with zero added dependency, in the same `do_GET`-on-`BaseHTTPRequestHandler` style as the existing handler. `http.server`'s docs describe `self.wfile` as a writable `io.BufferedIOBase` output stream for the response — [`docs.python.org/3/library/http.server`](https://docs.python.org/3/library/http.server.html) — and nothing in that stream's contract limits a handler to writing a body once; a `do_GET` can `send_response`/`send_header` once (declaring the multipart content type and boundary) and then loop, writing successive `--boundary...` chunks to `self.wfile` for as long as the connection stays open, exiting the loop (letting the handler method return) when a write fails/the client disconnects. This is a longer-lived `do_GET` than the JSON handler's, but structurally still just one `do_GET` method — no second server, no protocol upgrade.
- **Browser/OBS compatibility.** `multipart/x-mixed-replace` is handled by the living HTML standard's own image-fetching algorithm: the WHATWG HTML spec explicitly special-cases it in the `img` element's update-the-image-data steps, replacing the previous image each time a body part finishes decoding — [WHATWG HTML spec, "The img element"](https://html.spec.whatwg.org/multipage/images.html). It is a long-standing, browser-implemented pattern rather than a fresh/experimental one, though not something every MDN reference page enumerates (MDN's own "Common MIME types" list does not mention it) — so treat the WHATWG spec text as the primary citation here, not MDN's common-types page, which is silent on it. Both Firefox and Chromium have implemented `<img>`-driven MJPEG streaming for a long time; Chromium's support is narrowed to image content specifically (not arbitrary multipart documents) per community-documented behavior, since no single MDN/WHATWG compatibility table enumerates per-browser support for this legacy-but-universal pattern — flagged here as the one place this document leans on secondary sources (community bug trackers/blog posts) rather than a primary compatibility table, matching the caveat pattern this repo's `docs/research/typesafe-sdk-integration.md` §5 uses for its own single unverifiable figure. OBS's Browser Source is a bundled CEF (Chromium Embedded Framework) instance with, per its own project README, "complete access to modern web APIs" — [`obsproject/obs-browser` README](https://github.com/obsproject/obs-browser/blob/master/README.md) — so anything Chromium's `<img>` handles, OBS's browser source handles too; the OBS project's own docs make no free-standing MJPEG-specific caveat (nor did any OBS FPS/hardware-acceleration/cache setting get confirmed from a live obsproject.com page in this pass — the specific settings page fetched 404'd; the CEF/API-completeness claim above is the primary fact this document can stand behind).
- **Fit vs. the read-only/GET-only/loopback design.** Excellent fit — MJPEG is pure GET, no new HTTP verb, and (like the JSON endpoint) strictly server-to-client with the client never sending anything after the initial request. It slots into the existing `do_GET`-only structural pattern without modification to that pattern's guarantees.
- **Concurrency/threading.** This is the one place MJPEG genuinely differs from today's snapshot endpoint: the request thread stays open for as long as the viewer (OBS or a browser tab) keeps the connection alive, rather than the current request-and-done model. Under `ThreadingHTTPServer`'s one-thread-per-connection design — confirmed from `socketserver`'s docs, where `ThreadingMixIn` creates a new thread per request via `process_request()`, with `daemon_threads` controlling whether the server waits for those threads on shutdown — [`docs.python.org/3/library/socketserver`](https://docs.python.org/3/library/socketserver.html) — each MJPEG viewer simply holds one dedicated thread for the stream's lifetime. Given this project's stated audience (one OBS instance and/or one local browser tab, not many concurrent remote viewers), a small number of long-lived threads is a fine fit for the existing threading model, not a concern; it would become one only if the surface needed to support many simultaneous long-lived viewers, which is out of scope here.

## 4. Approach C — WebSocket binary frame push

**Mechanism:** an `Upgrade: websocket` HTTP handshake that hijacks the TCP connection into the WebSocket protocol (RFC 6455); the server then pushes binary frame data (e.g. raw pixels or encoded image bytes) over the upgraded, bidirectional connection, and client-side JS receives each binary message and draws it (e.g. to a `<canvas>`).

- **Implementation cost against stdlib `http.server`.** This is where WebSocket diverges sharply from the other two. Python's stdlib has no built-in WebSocket server support: neither `http.server`'s nor `socketserver`'s documentation mentions WebSockets, protocol upgrades, or any non-HTTP protocol handling anywhere — confirmed directly against both module pages — [`docs.python.org/3/library/http.server`](https://docs.python.org/3/library/http.server.html), [`docs.python.org/3/library/socketserver`](https://docs.python.org/3/library/socketserver.html). There is no `do_UPGRADE` hook or handshake helper anywhere in `BaseHTTPRequestHandler`. Building it by hand on `BaseHTTPRequestHandler` is possible — the handshake itself is a defined, if fiddly, computation: per RFC 6455 §4.2.2, the server must take the client's `Sec-WebSocket-Key`, concatenate it with the fixed GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`, SHA-1 hash the result, and base64-encode that hash as `Sec-WebSocket-Accept` — [RFC 6455 §4.2.2](https://datatracker.ietf.org/doc/html/rfc6455) — plus implementing RFC 6455's binary framing (opcode/mask/payload-length encoding) for every outgoing frame, all on top of a request/response-shaped handler class that was never designed to hold a hijacked socket open. This is buildable but nontrivial and unidiomatic against `BaseHTTPRequestHandler` specifically. The idiomatic path is the third-party `websockets` package, whose own docs describe it as building "upon `asyncio`, Python's built-in asynchronous I/O library," with a coroutine-based server API — [`websockets.readthedocs.io`](https://websockets.readthedocs.io/en/stable/) — meaning it would run as a second, separate asyncio-based server alongside the existing thread-based `ThreadingHTTPServer`, not as another `do_*` method on the same handler class; the docs note a "Sans-I/O" mode meant for embedding in other application servers, but reaching that integration is itself extra design work, not something `websockets` gives for free next to a `socketserver`-based server. Either path (hand-rolled or `websockets`) is a materially bigger lift than Approaches A or B, and the third-party-package path is a new dependency this project has so far avoided at the HTTP layer.
- **Browser/OBS compatibility.** Universally compatible in modern browsers — MDN's WebSocket API page marks it "Baseline: Widely available... well established and works across many devices and browser versions... available across browsers since July 2015," and documents binary payload support via `WebSocket.binaryType` (`ArrayBuffer`/`Blob`) for exactly the "push binary frame, draw to canvas" pattern this approach would use — [MDN, WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API), [MDN, `WebSocket.binaryType`](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/binaryType). Since OBS's Browser Source is CEF/Chromium with, per its own README, "complete access to modern web APIs" — [`obsproject/obs-browser` README](https://github.com/obsproject/obs-browser/blob/master/README.md) — WebSocket support there follows from Chromium's own long-standing WebSocket support; no OBS-specific WebSocket caveat was found in the sources reached during this pass (the dedicated OBS browser-source settings page returned a 404 when fetched directly, so this document cannot cite an OBS-specific quirks list beyond the README's general API-completeness claim).
- **Fit vs. the read-only/GET-only/loopback design.** This is the one place the three approaches genuinely diverge in spirit, not just cost. The handshake *starts* as an HTTP GET (with `Upgrade`/`Connection` headers) but then hijacks the connection into a different, non-HTTP, natively bidirectional protocol — so it does not slot into the "every method but GET gets a structural 501" framing the same way pure-GET approaches do; the read-only guarantee `stream_surface.py`'s docstring describes as "structural, not just by convention" (no write-capable `do_*` method exists) has no direct analogue once a socket is no longer speaking HTTP verbs at all. That said, a **push-only usage** — server sends binary frames, client-side JS never sends an application-level message back — would preserve the *spirit* of read-only even though the transport is technically capable of two-way traffic; it just can't be enforced the same structural way (by the absence of a handler method) that GET-only enforcement works today. Whether that's an acceptable tradeoff is a judgment call for #41, not something this document resolves.
- **Concurrency/threading.** A WebSocket server built on `websockets` runs its own asyncio event loop, entirely separate from `ThreadingHTTPServer`'s one-thread-per-request model — two different concurrency models coexisting in the same process (or two separate processes/ports) rather than one. A hand-rolled version on `BaseHTTPRequestHandler` would inherit the same long-lived-thread-per-viewer characteristic MJPEG has (§3), plus the added complexity of that thread now managing a bidirectional, framed protocol instead of a one-way byte stream.

## 5. What PyBoy 2.2.0 exposes for screen capture, and its cost

Read directly from the installed 2.2.0 package at `.venv/Lib/site-packages/pyboy` (the pinned version this repo actually runs, per `pyproject.toml`'s `pyboy==2.2.0`), rather than assumed from docs describing a possibly different version:

- `PyBoy` exposes a `screen` attribute — `self.screen = Screen(self.mb)` — constructed once per `PyBoy` instance — [`pyboy/pyboy.py:178`](../../.venv/Lib/site-packages/pyboy/pyboy.py) (installed package; not tracked in this repo's own source tree).
- `Screen` (in `pyboy/api/screen.py`) exposes, confirmed directly from its source and docstrings:
  - `screen.image` — "Reference to a PIL Image from the screen buffer... RGB image of (160, 144) pixels," built via `PIL.Image.frombuffer` over the live renderer buffer; `None`/a logged warning if Pillow isn't importable — [`pyboy/api/screen.py:98-124, 165-169`](../../.venv/Lib/site-packages/pyboy/api/screen.py).
  - `screen.ndarray` — a NumPy view over the raw buffer, shape `(144, 160, 4)` (row-major, RGBA) — [`pyboy/api/screen.py:126-163`](../../.venv/Lib/site-packages/pyboy/api/screen.py).
  - `screen.raw_buffer` — the underlying raw `bytes`, documented as exactly "92160 bytes of screen data" (`160*144*4`), with `raw_buffer_dims` = `(144, 160)` and `raw_buffer_format` = `'RGBA'` — [`pyboy/api/screen.py:35-97`](../../.venv/Lib/site-packages/pyboy/api/screen.py).
  - Screen resolution is corroborated by `pyboy/api/constants.py`: `ROWS = 144`, `COLS = 160` — [`pyboy/api/constants.py`](../../.venv/Lib/site-packages/pyboy/api/constants.py) — i.e. the standard Game Boy 160×144 display.
- Cross-referenced against PyBoy's own GitHub README (not version-pinned to 2.2.0, so treated as corroboration, not the primary source): it documents the same call, `pil_image = pyboy.screen.image` followed by `pil_image.save('screenshot.png')`, confirming the installed source's public surface matches the project's own current public documentation for this API — [`Baekalfen/PyBoy` README](https://github.com/Baekalfen/PyBoy). The README does not itself spell out `.ndarray` or the 160×144 figure; those are taken from the installed 2.2.0 source directly, which is the more authoritative source per this ticket's framing.
- **Encode cost.** A 160×144 frame is a small image by any modern standard — 23,040 pixels, 92,160 bytes raw RGBA per the docstring above. `pillow` is already a **direct** dependency of this repo (`pillow>=12.3.0` in `pyproject.toml`, not merely pulled in transitively through PyBoy), and PyBoy's `.image` already returns a `PIL.Image.Image`, so PNG/JPEG encoding is a one-line `img.save(buffer, format="PNG")`/`"JPEG"` — no new dependency for the encode path either way. At this resolution, PNG/JPEG encoding of a single frame is sub-millisecond-to-low-single-digit-millisecond work on any modern CPU — negligible next to the ~300ms per-turn budget this project already measured for the decision loop itself (`docs/turn-rate-budget.md`), and utterly negligible at the ~3.3 fps cadence this feed needs to sustain (one encode roughly every 300ms, not every 16ms as 60fps video would require).

## 6. Recommendation

**MJPEG (Approach B) for the video feed, continuing to reuse the existing JSON snapshot endpoint for the decision/confidence/milestone overlay data — no WebSocket.**

Reasoning, concretely for #41 to act on:

- **Stdlib-first, zero-added-dependency is achievable for both approaches A and B, but not for C.** WebSocket support does not exist in Python's stdlib `http.server`/`socketserver` at all (§4); getting it means either a nontrivial hand-rolled RFC 6455 implementation bolted awkwardly onto `BaseHTTPRequestHandler`, or a new third-party, asyncio-based dependency (`websockets`) running as a second server with its own concurrency model, alongside — not inside — the existing `ThreadingHTTPServer`. Neither is justified by this project's actual requirement (~3.3 fps, local-only).
- **MJPEG beats plain polling on smoothness for the same zero-dependency, same-structural-pattern cost.** Both A and B are pure GET and fit the existing `do_GET`-only handler shape with no changes to the read-only guarantees `stream_surface.py` already documents as structural. But MJPEG pushes each new frame the moment it's ready over one held-open connection, rather than depending on a client-side polling interval to approximate the same thing with extra per-tick connection overhead — and it does this with a `<img src="...">` tag needing zero client-side JS, simpler than either the polling approach's timer/cache-busting logic or a WebSocket approach's `<canvas>` draw loop.
- **The concurrency cost MJPEG adds (one held-open thread per viewer) is a non-issue at this project's scale.** The audience is one OBS browser source and/or one local browser tab (§0/background), not many concurrent remote viewers; `ThreadingHTTPServer`'s one-thread-per-connection model (§3) absorbs that trivially. This would need re-evaluating only if the surface ever had to serve many simultaneous long-lived viewers, which is out of scope for this project as described.
- **~3.3 fps needs none of WebSocket's extra machinery.** WebSocket's real advantages — lower per-message framing overhead, true low-latency bidirectional messaging — matter at video-game-footage cadences (30-60fps) or when the client needs to talk back. Neither applies here: the cadence is set by a ~300ms tactical decision loop (§1), and every approach considered is push-only from server to client (the "fit vs. fight" concern in §4 that WebSocket raises around bidirectionality is moot if nothing pushed to a WebSocket server would ever be read back).
- **Reuse, don't merge, the existing JSON endpoint for overlay data.** The decision/confidence/milestone JSON snapshot `stream_surface.py` already serves has no reason to move onto the MJPEG connection or be re-encoded as part of the frame stream — it's a separate concern polled independently (as it already is), and combining them would only complicate both the MJPEG byte stream and the JSON contract for no benefit at this scale. A browser page (and an OBS browser source, which is just a browser page) can trivially run both: an `<img>` pointed at the MJPEG endpoint for video, and the existing polling JS against the JSON endpoint for the overlay, composited with plain CSS/HTML.
- **Encode path needs nothing new.** PyBoy's `screen.image` already returns a `PIL.Image.Image` at 160×144 (§5), and Pillow is already a direct dependency — encoding each MJPEG part is `image.save(buffer, format="JPEG")`, and cheap enough at this resolution/cadence to not be a design concern.

What #41 still has to decide (left open deliberately, since this document is tradeoffs, not a spec): the JPEG quality/size tradeoff for the MJPEG parts, the exact boundary/loop shape of the long-lived `do_GET` handler, and whether the MJPEG endpoint lives on the same server/port as the existing JSON snapshot endpoint or a second one.
